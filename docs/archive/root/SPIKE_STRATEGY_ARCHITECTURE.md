# 1s 逼空插针策略系统整体架构方案

> 历史草案，非当前实现依据。当前以 `PLATFORM_ARCHITECTURE.md` 和 `docs/spike_trader/` 为准；本文中的 tick/纸盘表述不代表新版运行模式。

## 1. 目标与定位

本系统面向 1s/tick 级别的逼空加速、极端拉升和插针回落场景，核心动作是：

1. 持续监听成交事件和短周期市场结构。
2. 识别加速前起涨点、短时动能放大和成交量异常。
3. 在满足起涨点约束后，预测极端价格区间。
4. 通过多档限价单参与冲高回落做空。
5. 管理部分成交、撤单、重挂、止损、止盈和超时退出。

该系统应作为独立的事件驱动交易系统运行，不作为现有 K 线交易框架中的普通策略插件。现有交易逻辑不应被改造成适配该策略。

## 2. 系统边界

系统独立拥有：

- 行情接入与事件处理
- 1s/tick 特征计算
- 插针识别和价格预测
- 多档订单状态机
- 持仓和退出逻辑
- 独立风控
- 实时回放和回测
- 运行监控与故障恢复

可以复用的内容仅限于中性的底层能力，例如交易所协议适配、网络工具、日志、指标和告警。不得复用现有系统的信号生命周期、订单状态机、持仓决策或退出规则。

## 3. 总体架构

```text
Binance WebSocket
  ├─ aggTrade / tick
  ├─ mark price
  ├─ order book
  └─ liquidation data
          ↓
行情标准化、去重、排序和质量检查
          ↓
每个币种独立的事件处理器
          ↓
1s 窗口、涨速、成交量、波动率计算
          ↓
逼空/插针识别器
          ↓
价格预测与多档挂单计划
          ↓
独立风险管理
          ↓
订单管理与执行
          ↓
交易所
```

所有行情、订单、成交和仓位变化都应写入事件日志，供实时系统、故障恢复和回测系统共同使用。

## 4. 策略规则要求

### 4.1 触发条件

- 必须确定加速前的起涨点。
- 当前价格相对起涨点上涨至少 10%，这是硬性条件。
- 必须出现 1s/tick 级别的明显加速，不能只依据完成的 1m K 线涨幅。
- 短时间收益率、成交量倍数和波动率应同时放大。
- 价格需处于近期低点上方足够距离，减少普通震荡误判。
- 点差、盘口深度和可成交金额必须满足约束。

V1 的具体阈值应冻结为配置版本，并记录每次回测和实盘使用的参数，不能在运行中无审计地修改。

### 4.2 价格预测

- 优先使用实时动能、近期极值、ATR 和成交结构估算极端价格。
- 有清算地图时，将清算密集区作为价格锚点或修正项。
- 没有清算地图时，使用程序估算值，不能引用其他日期的固定历史价格。
- 每个预测价格必须标记来源：清算地图、动能估算或混合估算。

### 4.3 多档挂单

- 默认使用三档挂单，例如 30% / 40% / 30%。
- 挂单价格围绕预测极值和回撤区间生成。
- 每档拥有独立状态：未挂、已挂、部分成交、完全成交、撤销、失效。
- 每档订单具有明确 TTL，过期必须撤销。
- 动能继续扩张时，允许滚动重算价格，但必须限制重挂次数。
- 超过失效价格后禁止继续开仓。

### 4.4 退出规则

- 硬失效价优先执行，尽可能使用交易所托管止损。
- 止盈目标按风险距离计算，不使用无法解释的固定价格。
- 设置最大持仓时间。
- 同一事件同时触达止损和止盈时采用保守结果。
- 数据断线、延迟或订单状态不一致时，禁止新增仓位并进入保护状态。

## 5. 核心状态机

```text
Idle
  → Monitoring
  → Triggered
  → OrdersPlaced
  → PartialFilled / FullyFilled
  → PositionOpen
  → ExitPending
  → Closed
  → Cooldown
```

必须处理以下异常状态：

- 部分成交后撤销剩余订单
- 下单成功但本地未收到确认
- 撤单成功但成交回报延迟
- 进程重启后从交易所恢复订单和仓位
- 重复事件不产生重复订单
- 单个币种异常不影响其他币种

## 6. 数据架构

实时路径不应依赖 DuckDB 或长时间运行的分析查询。

- 热数据：内存环形窗口，保存最近数分钟至数小时的事件。
- 原始行情：追加写入 Parquet、对象存储或 ClickHouse。
- 订单、成交和仓位：事务型数据库持久化。
- 回测数据：从原始事件日志重放，而不是只依赖预聚合的 1s K 线。
- 每条事件包含交易所时间、接收时间、序列号、数据源和质量标记。
- 必须检测断档、乱序、重复事件和本地时间漂移。

实时和回测应使用同一个策略核心，只替换事件来源：

```text
实时 WebSocket 事件 → 策略核心
历史事件回放       → 同一个策略核心
```

## 7. 独立风控

逼空策略的主要风险是价格继续扩张导致空头快速亏损，因此必须独立设置：

- 单币最大名义仓位
- 全局最大持仓
- 单币最大挂单数量
- 单日最大亏损
- 连续止损后的冷却时间
- 最大持仓时间
- 最大订单重试次数
- 数据延迟阈值
- 盘口深度不足时禁止挂单
- 全局紧急停止和撤单按钮

实盘初期建议使用独立 API Key 或子账户，避免其他交易系统误撤销或接管本系统订单。

## 8. 订单执行要求

订单执行器必须支持：

- 限价单、撤单和重挂
- 部分成交
- 订单状态幂等
- 交易所回报与本地状态对账
- 价格和数量精度校验
- 独立的 `clientOrderId` 命名空间
- 网络重试和超时恢复
- 交易所异常时的保护动作

策略只能生成订单意图和订单计划，不能绕过风险层直接调用交易所。

## 9. 回测要求

- 使用原始 aggTrade/tick 事件，而不是只使用 1s K 线。
- 回测必须严格按事件时间顺序执行。
- 禁止使用触发事件之后才完成的 K 线高点、成交量或其他信息。
- 对限价单采用保守成交模型，区分触价、成交和部分成交。
- 模拟手续费、滑点、订单延迟、盘口深度和撤单失败。
- 实时和回放必须使用同一状态机。
- 每次回测保存数据版本、策略版本、参数版本和结果摘要。

## 10. 监控与告警

至少监控以下指标：

- 行情延迟和事件断档
- 事件队列长度
- 触发次数和挂单次数
- 成交率、部分成交率和撤单率
- 下单延迟和交易所拒单
- 订单状态对账差异
- 持仓、保证金和未实现盈亏
- 单币及全局回撤
- 进程重启次数和恢复结果

必须提供一键撤单、禁止新开仓和全局停止功能。

## 11. 部署方式

第一版不需要拆成大量微服务，一个独立进程即可包含：

```text
行情接入 → 策略状态机 → 风控 → 订单管理 → 交易所
```

实时系统、历史回放和报告生成可以作为不同运行模式，但必须共享同一策略核心。生产部署应与现有交易服务隔离进程、配置、日志和 API 凭证。

## 12. 上线阶段

1. 冻结事件格式、策略规则和参数版本。
2. 建立原始事件存储和确定性回放器。
3. 完成无未来数据的逐事件回测。
4. 运行纸面交易，比较实时触发和历史回放结果。
5. 使用测试网或独立子账户小额运行。
6. 只开放少量币种和极低仓位进行灰度。
7. 完成订单、成交、仓位和余额对账后再扩大规模。

## 13. 最终架构决策

本策略采用：

> 独立进程、独立数据流、独立策略状态机、独立订单状态和独立风控；只在需要时复用最底层的交易所协议和监控能力。

这样可以保持现有交易系统不变，同时为 1s/tick 事件驱动、动态多档挂单和高风险空头管理提供完整的运行边界。

## 14. 当前回测文件说明

本次 2026 年 7 月 100 标的回测实际使用的是独立动态 1s 插针策略脚本，不是现有 K 线策略插件：

- `scripts/backtest_dynamic_spike.py`：单币种动态插针触发、预测价格、三档挂单和触达结果计算。这里包含本次回测的策略规则。
- `scripts/append_dynamic_spike_pnl.py`：根据触达档位计算入场价、止损/止盈/超时退出和净收益。这里包含本次回测的实验性退出口径。
- `scripts/batch_backtest_dynamic_spike.py`：批量并行调用上面两个脚本，只负责调度，不改变策略逻辑。
- `scripts/summarize_dynamic_spike.py`：统计触发、挂单、成交、仓位、胜率和 Profit Factor，不参与交易决策。

本次批量结果位于 `reports/dynamic_final_run1/`，其中 `all_trigger_orders_with_pnl.csv` 是合并后的逐笔明细，`summary.json` 是汇总结果。

`src/crypto_trader/signals/strategies/high_volume_top.py` 是现有框架中的另一套 K 线策略实现，本次动态 1s 插针批量回测没有直接调用它；两者应在后续独立系统设计中明确区分。
