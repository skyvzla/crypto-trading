# 项目完整实施计划

> 版本：v1.0
> 日期：2026-08-06
> 当前状态：参数已冻结，P0 运行缺陷与 replay 入口已修复

## 一、目标与范围

在现有三层架构上，完成一条可审计的 Spike 做空策略闭环：

```text
行情接入 -> 完成 1s Bar -> 监听池 -> Spike 信号
-> Campaign -> 三档订单 -> 成交/持仓
-> 保护与退出 -> PostgreSQL 账本 -> Web 查询与控制
```

V1 只实现上涨尖峰后的做空策略。清算地图、其他策略和未经确认的实时纸盘不纳入实施范围。

## 二、阶段与验收

### Phase 0：脚本基线冻结与测试案例建立

**状态**：参数已冻结（2026-08-06），待建立固定测试案例。

**目标**：以 `scripts/backtest_dynamic_spike.py` 为唯一事实源，冻结所有触发、价格、失效和窗口参数；建立固定测试案例验证新代码与脚本的可解释差异。

**已完成**：
- ✅ 三档价格公式修复（`range(3)`）
- ✅ 参数冻结到 `decisions.md`
- ✅ 新代码消除未来数据泄漏（spike_high、ATR 只用已完成 K 线）
- ✅ 通用与专用 Spike replay 入口接通
- ✅ testnet URL、订阅刷新和 combined stream P0 修复

**待完成**：
1. 建立 5 个固定测试案例（无成交、部分成交、失效、三档全成交、信号冷却）
2. 对照脚本 CSV 输出，验证新代码触发时机、三档价格的偏差可解释
3. 记录回测口径（部分成交、手续费、滑点、未平仓结算）

**验收条件**：
- 相同历史数据，新回测引擎与脚本的触发事件≥90%重合
- 差异可逐笔解释（未来数据消除导致触发提前几秒属正常）
- 固定案例可重复得到相同结果

### Phase 1：数据层运行闭环

目标：让行情层可靠地产生可消费的完成 1s Bar。

工作：修复 testnet URL 隔离、combined stream 解包、订阅路由冲突、WebSocket 重连、聚合窗口多根 Bar 丢失、健康检查和数据质量标记；补 Redis/WS/FastAPI 集成测试；设计 Parquet/DuckDB 归档边界。

验收：测试网配置绝不连接生产 URL；PUT 订阅确实刷新流；combined stream 能产生 Bar/Kline；断线和重启后订阅可恢复；缺口和预热不足会阻止信号。

已完成：testnet 隔离、combined stream 解包、订阅刷新、自动重连、并发刷新保护、
按币种构建 streams、多根完成 Bar 全量发布、已发布窗口迟到数据防重复，以及
Redis/WS readiness 健康检查和故障 HTTP 503。

### Phase 2：统一策略核心与 Campaign

目标：实时与 replay 使用同一份无环境依赖的策略核心。

工作：策略只接收标准事件、时钟和账户/订单状态；输出订单意图；实现 Campaign 生命周期、全局互斥、逐币种状态、冷却、失效和第一笔成交计时。

验收：相同事件序列在 replay 和实时适配器中产生相同策略决策；不会出现重叠交易轮次；所有已确认生命周期规则均有测试。

已完成：replay 多币种全局准入互斥、成交回报按币种路由、第一笔真实成交时间记录。

### Phase 3：可信 replay 回测

目标：接通统一 runner，获得可解释的历史回放结果。

工作：删除过期 Spike runner API；接入完成 Bar 和已完成辅助 K 线；禁止未来数据；实现订单触价、部分成交、撤单、手续费、滑点、退出和未平仓结算；输出触发、预测、订单、成交、退出和 PnL 审计报告。

验收：`--strategy spike` 可实际运行；固定案例全通过；原实验基线与新结果差异可以逐笔解释；缺少数据时明确拒绝而不是联网补数据。

已完成：两个 Spike CLI、UTC 时间、16 小时只读预热、必需数据缺失拒绝、
信号至三档成交的离线正向回归、未平仓状态与最后价未实现盈亏、手续费单次扣除。

### Phase 4：执行与恢复

目标：在不破坏 Campaign 约束的前提下完成测试网执行。

工作：实现 clientOrderId 幂等、WAL、`SUBMIT_UNKNOWN` 后台查询、启动对账、User Stream 回执、部分成交、撤单竞态、迟到回报和持仓事实同步；实现交易所托管保护单。

验收：网络超时不会重复开仓；未确认状态会阻塞相关账户/币种新开仓；重启后未终态轮次可恢复；成交和持仓以交易所事实为准。

### Phase 5：账本控制层与测试网

目标：提供最小可用的 subcategory 控制、账本查询和运行状态。

工作：补 PostgreSQL/Redis/FastAPI Compose 集成测试；实现 Web 首版确认的控制范围、权限和审计；接入策略账本写入、控制状态轮询、健康检查和告警。

验收：subcategory 关闭只撤未成交入场单，已有仓位继续保护；账本可查询完整生命周期；测试网账户与正式账户隔离；异常时默认禁止新开仓。

### Phase 6：正式账户灰度

前置：Phase 0-5 全部完成并由人工确认。

工作：固定小额名义金额、少量 subcategory、值守、告警、备份、回滚和紧急平仓演练。

验收阈值、灰度周期和扩大条件必须在启动前写入决策记录，不使用旧文档中的 PF 阈值作为默认标准。

## 三、优先级

## 四、禁止事项

- 未冻结策略规则前，不修正三档价格、退出或阈值为自认为合理的版本。
- 未完成测试网隔离前，不使用真实 API Key 启动策略。
- 不把研究报告收益当作生产收益承诺。
- 不新增清算地图、其他策略或实时纸盘，除非决策记录明确批准。
