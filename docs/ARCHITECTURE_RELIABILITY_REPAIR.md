# 架构可靠性修复

分支：`fix/architecture-reliability-20261009`。本次修复运行协议与数据衔接，保留现有策略参数、专用账户边界和 Long Breakout 的 4h／1d 收盘退出规则。

## 行情交付

- 订阅变化先停止消费，再调整流状态；保留流沿用内存水位与未完成秒桶，冷启动才恢复 Redis 水位。后台回补与订阅调整互斥，避免重建已经取消的聚合窗口。
- Redis 原子提交完成事件、提交水位及 K 线 latest。重试不会重复追加，同一事件身份但内容不同会拒绝；Pub/Sub 仅负责通知。发布未确认的完整 Bar 保留在内存待提交队列中。
- 秒线使用 `bar1s:stream:{symbol}`，闭合 K 线使用 `kline:stream:{symbol}:{interval}`。短期保留分别约 900、1500 条；Redis Stream ID 是传输游标，业务连续性依据成交 ID 和 K 线时间。
- 流独立消费、回补和退避重试。每轮最多 20 页、30 秒，失败后保留已验证进度；对外秒线缺口接口最多回补 20000 笔成交。较大、不可验证的策略消费缺口触发受控重启，重新对账并完整预热，不以若干新 Bar 掩盖缺口。
- `/health`、`/quality` 支持 `consumer_id`，运行中的策略按自身订阅判断就绪。接收时间与事件时间均参与新鲜度判断，Pub/Sub 接收人数保留为诊断信息。

## 周期与回测

- 策略声明最低历史需求，独立于缓存容量。V22 默认至少需要连续 10080 根 1m、15 根 5m、10 根 15m。
- 预热通过 Market API 获取固定 UTC 截止点的完整窗口，最多 1500 根一页；校验首尾、内部缺口、闭合时间和冲突重复。线上不启动归档器或历史批量下载任务。
- 预热及缺口回放用于恢复缓存，不补发过期交易意图。实时事件按可用时间、事件类型、币种和周期排序，同刻先秒线后 K 线；使用有限乱序缓冲，等待缺少的闭合 K 线时关闭入场。
- 正式回测默认验证完整覆盖后才输出事件。分钟及更长 K 线验证完整时间网格；秒线验证日分区与成交 ID 连续性，合法无成交秒允许稀疏。没有成交 ID 的秒线必须能证明完整秒网格。
- `validate_coverage=False` 仅保留给底层稀疏数据读取工具；正式回测入口使用默认严格校验。回测继续只读 DuckDB／Parquet，不读 Redis、不联网补数据、不回写归档。

## 执行与持久化

- 所有订单状态写入在 WAL 同一临界区读取最新事实后合并。较晚到达的超时、旧快照不能覆盖已确认状态；交易所订单 ID 冲突保持硬失败。
- 未知订单监控常驻，结合事件唤醒与退避查询；只查单，不盲目再次 POST。事实恢复后重新对账、恢复持仓和 Campaign 时序，再恢复执行。临时未知提交不会成为只能重启清除的风险 halt。
- 新增 PostgreSQL 迁移 `0025_execution_jobs.sql`。执行意图先持久化，再进入现有账户 worker；账户独占租约继续负责单写者边界。
- 重启时，已由订单 WAL 接管的任务完成交接；未提交的旧入场信号标记过期，等待新信号。退出任务保留，并根据当前仓位、在途订单和方向重新确认数量；执行能力暂时不可用时等待重试。
- 两个策略共用公共执行队列，删除 Spike 的重复兼容导出层。
- 生产运行中的审计先写本地 fsync 日志，后台独立镜像 PostgreSQL。数据库等待不占用追加锁；确认后原子保留未镜像的尾部，失败或重启继续重放。

## 发布与限制

- PostgreSQL、Redis 使用 `unless-stopped`。基础服务通过现有安全部署入口发布，保留策略启停、通知和账户门禁。
- 发布前验证 PostgreSQL 备份能恢复；新任务表纳入后续备份数量校验。迁移是增量添加，现有迁移文件不改写。
- 旧镜像不能直接越过严格的数据库版本检查。回退前必须排空并对账，使用兼容迁移清单的修复镜像；不能用旧账本覆盖部署后产生的新成交。
- 本轮没有启用策略或发送真实订单。私有测试网订单闭环、交易所断流及实际持仓演练仍须在启用策略前完成。
- Long Breakout 仍按所选周期收盘判断退出，没有新增盘中保护规则；止损阈值不等于最大亏损上限。
